# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev        # Vite dev server on http://localhost:3000 (alias: npm start)
npm run build      # `tsc && vite build` — tsc is the only type check; there is no separate script
npm run preview    # serve the production build
```

There is **no linter, formatter, or test runner** configured. To verify a change, run `npx tsc` (or `npm run build`) and exercise the page in the dev server.

Stack: React 19, TypeScript (strict), Vite, Tailwind CSS v4 (via `@tailwindcss/vite`, no `tailwind.config` — tokens live in CSS), Redux Toolkit, React Router v7.

TypeScript flags that bite: `verbatimModuleSyntax` (type-only imports must use `import type`), `erasableSyntaxOnly` (no `enum`, `namespace`, or constructor parameter properties), and `noUnusedLocals`/`noUnusedParameters` (prefix an intentionally unused parameter with `_`, as `requestPasswordReset(_email)` does).

## Architecture

`src/README.md` documents the module layout and dark-mode rules — read it before adding a page. The parts that matter most:

- **Organised by feature module** (`src/modules/<name>/`), with `app/` wiring them together (routes in `App.tsx`, store in `store.ts`) and `shared/` for anything used by 2+ modules. Cross-module imports go through the module's `index.ts`, never into its internals, and `shared/` must not import from `modules/`.
- **Strings, constants, and types are split out of components.** A component `Foo.tsx` has its copy/constants in `constants/foo.const.ts` and its types in `models/foo.model.ts` (e.g. `LoginPage.tsx` imports every label from `login/constants/login.const.ts`). Follow this when adding UI instead of inlining text.
- **Typed Redux hooks**: use `useAppDispatch` / `useAppSelector` from `src/app/hooks.ts`, not the raw react-redux hooks.

### Auth is a mock

`modules/auth/shared/authApi.ts` simulates latency and validates against `data/dummyData.ts` — there is no backend. Its function signatures are the contract; swap the bodies for real HTTP calls and the rest of the app (thunks in `authSlice.ts`, pages) should not change. Demo login: `demo@checklist.app` / `password123`. Sign-ups are pushed into the in-memory `dummyUsers` array and vanish on reload.

Auth state (`state.auth.user`) lives only in Redux — it is not persisted, so a page refresh logs the user out (a full page load, e.g. typing a URL, also logs you out; navigate in-app instead).

Thunks in `authSlice.ts` throw from the API layer and surface `action.error.message` into `state.error`; pages call `dispatch(thunk(...))` and check `thunk.fulfilled.match(result)` before navigating.

### The logged-in app: `AppShell` and the checklists domain

Every logged-in route is a child of `<AppShell>` in `src/app/App.tsx`. `AppShell` is the **only auth guard** (redirects to `/login` when `state.auth.user` is null), renders the sidebar, and owns the initial data load. Pages under it can assume workspace data is already in the store and read the signed-in user with `useCurrentUser()` (outlet context — it only works for components rendered inside the `<Outlet>`, so `Sidebar` gets `user` as a prop instead). Add new logged-in pages as children of that route and build links from `src/shared/constants/routes.ts`.

- `modules/checklists` is the domain: models mirror the ERD (workspaces, members, tags, checklists, items, comments), `checklistsApi.ts` is a **mock** like auth's (swap the bodies for HTTP; signatures are the contract), `checklistsSlice.ts` holds everything in one normalized-by-arrays slice, and `selectors.ts` has memoized lookup Maps (`selectPeopleById`, `selectItemsByChecklistId`, …) — use those rather than `.find()` in rows. It also owns `ChecklistPage` (tabs Items / Activity / Members). `modules/dashboard` is just the list views (`view` prop: all, dueSoon, templates, assigned, workspace).
- Item/comment/tag changes are **not optimistic**: the UI updates when the thunk resolves (mock latency is 150ms). Their failures set `state.mutationError`, shown as one banner by `AppShell`. The dialogs (new workspace/checklist, edit checklist, share) instead `unwrap()` their thunk and show the error inline — rejected thunks throw a plain `SerializedError`, so read `.message`, don't use `instanceof Error` (`messageOf` in `utils/checklistUtils.ts`).
- Tags belong to a workspace, and a *checklist* picks which of them it uses; its *items* can only use the checklist's own tags (invariant: `item.tagIds ⊆ checklist.tagIds`). Creating a new tag happens only in the checklist form, never on an item.
  - **Checklist form.** `NewChecklistDialog` and `EditChecklistDialog` are thin wrappers around the shared `ChecklistForm` (title, workspace, tags, due date, "Save as a template"); they differ only in the starting values and in what `onSubmit` does. The form uses `useTagSelection(workspaceId, initialTagIds)` + `<TagField>`: tick existing tags or type new ones; typed names are only turned into real tags by `resolveTagIds()` on submit (so cancelling leaves nothing behind, and a name typed but not yet added still counts). Ticked tags are cleared when the workspace changes (`clearSelection`). When creating, the workspace starts as `null` ("Select a workspace") unless the dialog was opened from a workspace page, tags stay locked until one is chosen (`useTagSelection(null)` → `isEnabled: false`), and submitting without one is refused. The due date can't be a past day (`min` is today, and a typed-in past date is refused); a past date the checklist already has (it's overdue) may stay, so it can still be renamed without touching the date.
  - **Items.** `AddItemRow` and `ItemDetails` show the checklist's tags with `ChecklistTagList` (`useChecklistTags`) and have no add-tag input; a checklist with no tags says so and points to editing the checklist.
  - **Item due dates.** An item's due date must be *before* the checklist's due date (the day itself and later are greyed out in the picker, and a typed-in one is refused): `useItemDueDateMax(checklistId)` gives the date input's `max` (the day before the checklist's due date; none when the checklist has no due date). Both `AddItemRow` and `ItemDetails` use it. That covers what can be picked; for dates already set, `updateChecklist.fulfilled` keeps the rule when a checklist's due date moves earlier: every item due on or after the new date is pulled back to the day before it (due Nov 1 → items at most Oct 31), and items already earlier keep their date. The Edit checklist dialog says how many items will move before you save (`dueDateHint`). Moving the date later, or clearing it, changes no item.
  - **Keeping the invariant.** `updateChecklist.fulfilled` drops a tag from the checklist's items when it's taken off the checklist, and after a *move to another workspace* it also clears the item tags, unassigns items whose assignee isn't a member of the new workspace and removes role rows of people who aren't members. A real backend must do the same cascade.
- **Per-checklist roles** (three, plus the creator). A person is `creator` (`checklist.createdBy`: acts as an Admin, can't be demoted, has no row), `admin` or `superuser` (a `checklistRoles` row each, one per person per checklist, replaced when the role changes), or the default `user` (no row). The rules live in one file, `utils/permissions.ts`, and components ask `useChecklistRole(checklistId)` (`role`, `canManageChecklist`, `canManageItems`):
  - **Admin**: everything below, plus edit and delete the checklist, add new checklists, and give or take away the Admin and Superuser roles.
  - **Superuser**: add, edit (assignee, due date, tags) and delete items, and give or take away the Superuser role only.
  - **User**: nothing extra. **Every role** can tick items off and comment.
  - `canChangeRole(viewer, target, next)` decides role changes (both the role taken away and the one given must be managed by the viewer; the creator never changes) and `roleOptionsFor` feeds the Members tab's role picker, so it offers only what the viewer may set. Every member's role is also shown as badges next to their name, to *every* viewer, whether or not they can change it (`roleBadgesFor`: the creator gets both "Creator" and "Admin", everyone else their one role); the picker is just the extra control on the right. Each badge is a `RoleBadge` with an "i": hovering or focusing it shows what that role can do (`roleDescriptions` in `checklistPage.const.ts` — keep it in step with `utils/permissions.ts`), so the tab has no help paragraph. The list is sorted by that hierarchy (`compareRoles`: creator, admins, superusers, users; A-Z within a group) and re-sorts as soon as someone's role changes.
  - *Adding a checklist* is workspace-level, so it also opens to whoever owns or administers the workspace (there's no checklist yet to hold an Admin role): `canCreateChecklistIn` / `useCreatableWorkspaces`. The dashboard hides "New checklist" when that list is empty (but not for someone with no workspaces at all, whose dialog tells them to make one), and the New/Edit checklist dialogs only offer those workspaces. Inviting people to the workspace isn't covered by the roles.
  - These checks only decide what the UI offers — the mock API trusts it, so a real backend must enforce them. The UI hides what a role can't do instead of disabling it.
- **Comments are separate from editing.** Because every role can comment but only some can edit, an item has two independent boxes: the speech-bubble button (`CommentToggleButton`, with a count badge) opens `ItemComments`, and the pencil opens `ItemDetails`. They can be open together. Comments work on completed items too.
- **Deletion rules** (`utils/deletion.ts`): an item can be deleted only once it's completed; a checklist only when it has no items or every item is completed. Deleting a checklist also removes its items, comments and role rows (tags stay — they belong to the workspace). On top of that, deleting an item needs `canManageItems` and deleting a checklist needs `canManageChecklist`; the rule only decides *when* it's allowed. Like the role checks, these only decide what the UI offers; a real backend must enforce them. The confirm-then-delete logic lives in `useDeleteItem` / `useDeleteChecklist`, shared by every delete control: the trash icon on each `ChecklistCard` (shown to admins only, disabled with the reason as its tooltip) and on each *completed* `ItemRow` (shown to admins and superusers; open rows have no icon, and the item panel has no delete control), plus the checklist page's "Delete this checklist" section (admins only). Their hover text comes from the shared `Tooltip` (CSS-only, so it works on disabled buttons): the checklist controls say why they're disabled, and the row icon names the item. The page passes a callback to `requestDelete` that navigates away *before* the delete is dispatched, because once the checklist leaves the store the page would flash "not found".
- `ChecklistCard` is a `div`, not a link: only the title is a real `<Link>`, stretched over the whole card with `after:absolute after:inset-0`, because the trash `<button>` can't live inside an `<a>`. Anything clickable inside the card needs `relative z-10` (see `DeleteIconButton`) or the overlay will swallow its clicks.
- **Editing.** A pencil (`EditIconButton`) sits beside the checklist title, on each `ChecklistCard` (next to the trash icon) and beside each item's name. The checklist ones open `EditChecklistDialog` (all the checklist form's fields, through the `updateChecklist` thunk) and are shown to admins only. The item's toggles that item's inline `ItemDetails` panel (`aria-expanded`); the item name itself is plain text, not a button. It sits at the right edge of the row, next to the trash icon, and only *open* items have it, and only for admins and superusers: a completed item is read-only (no pencil, no edit panel), and ticking an item off closes its panel. Each row's right-hand buttons are fixed 28px slots (comment, pencil, trash, with an empty slot where one doesn't apply) so each kind stays in one column.
- The slice resets to its initial state on auth `logout`, and `loadWorkspaceData` has a `condition` that skips it unless status is `idle`/`failed` (React StrictMode runs effects twice in dev).
- Dummy data is rebuilt on every load with dates relative to today (so "Due soon" and overdue styling never go stale). Person ids there are deliberately not `user-N`: the auth mock mints `user-2`, `user-3`, … for sign-ups, which must not inherit someone's workspaces. A brand-new sign-up therefore starts with no workspaces. Invites look people up by email in `dummyDirectory` (e.g. `sara@acme.co` is invitable into "Design team").

**Where the UI goes beyond the ERD** (needs backend support before wiring to a real API): the mockup shows a **due date and tags on each item**, but `checklist_items` has no `due_date` and tags only attach to checklists (`checklist_tags`), so items carry `dueDate`/`tagIds` here. There is **no activity/audit table**, so the Activity tab is derived from existing timestamps and can't name who added or completed an item. **Share** is workspace-level (invites into `workspace_members`), since the ERD has no per-checklist access. **Checklist roles** have no table: the ERD only has the workspace-level `workspace_members.role`, so per-checklist admins and superusers need something like `checklist_roles(checklist_id, user_id, role, granted_by, granted_at)` (the creator stays implicit via `checklists.created_by`, and a plain user has no row). The Members tab shows that per-checklist standing, not the workspace role. `workspace_members.role` has no listed values; `owner | admin | member` is assumed.

### Theming (two files must stay in sync)

- Brand colors are defined twice: as Tailwind tokens in the `@theme` block of `src/shared/styles/index.css` and as values in `src/shared/styles/theme.ts`. Change both together.
- Components should use the exported class tokens from `theme.ts` (`surface.*`, `text.*`, `toneClasses`, `linkClasses`, …) rather than raw `bg-white` / `text-neutral-900`; each token already carries its `dark:` pair. A bare color class stays the same in dark mode.
- Form controls: use the shared `Select` instead of a raw `<select>` (the browser's native arrow ignores padding and sits flush against the edge; `Select` hides it and draws its own inset chevron), Every text field should have a "×" once it has text: the labelled `Input` shows one by itself for text-like types (opt out with `clearable={false}`; it needs a controlled `value`), `PasswordInput` adds its own next to Show/Hide (use it for every password field, including reset-password), and bare inputs (item title, tag names, date pickers) use `ClearableInput`, and multi-line text (the comment box) uses `ClearableTextarea` with `textareaFieldClasses` (Enter adds a line, Ctrl/Cmd+Enter posts). A `Select` whose empty option means "none" (Workspace's "Select a workspace", Assignee's "Unassigned") takes `onClear` + `clearLabel` and shows the same "×" while it has a value; leave them off when a value is always required (the Members tab's role picker). The "×" is `ClearButton`, deliberately out of the Tab order (`tabIndex={-1}`); `clearInputValue` in `shared/utils/dom.ts` is how it empties a controlled input so the caller's `onChange` still runs. `Button` already carries `cursor-pointer` (and `cursor-not-allowed` when disabled), so don't add it per call site.
- `Modal` (native `<dialog>`) does **not** close when you click outside the box, so a stray click can't discard a half-filled form; it closes with the "×", a Cancel button or Escape. React's `autoFocus` is lost inside it (it runs before the native dialog is open, and `showModal()` then focuses the "×"), so a field that should start focused uses `data-autofocus` instead; `Modal` focuses it after opening and selects any text in it.
- **Confirmations never use `window.confirm`/`alert`.** Ask with the shared `useConfirm()` (`shared/hooks/useConfirm.ts`): `const confirmed = await confirm({ title, message, name, confirmLabel, tone: "danger" })` resolves `true`/`false`. `ConfirmProvider` (mounted once in `app/App.tsx`) renders the single `ConfirmDialog`, built on `Modal`, so a feature needs no dialog of its own. Put `{name}` in the `message` and pass `name`: it's swapped in, in bold (e.g. the title of what's being deleted). Focus starts on Cancel, and a click outside doesn't dismiss it (same as `Modal`). The item and checklist deletes use it, with their text in `checklistItem.const.ts` / `checklistPage.const.ts`.
- `surface.border` colors an element's *own* border; for `divide-y` use `surface.divide` (a `border-*` class does nothing to the borders `divide-y` draws on children, so they fall back to black).
- Dark mode is class-based (`dark` on `<html>`), managed by `src/shared/hooks/useTheme.ts`. The same logic is duplicated in an inline script in `index.html` to avoid a flash on first paint — the `localStorage` key `checklist-theme` must match in both places, and `TRANSITION_MS` in `useTheme.ts` must match the transition duration in `index.css`.

### Assets

The Museo Sans `@font-face` rules in `index.css` point at `src/assets/fonts/*.woff2`, which are not in the repo (the font is commercial); the sans-serif fallback is what renders. The tab icon is `public/favicon.svg`, referenced from `index.html`.
